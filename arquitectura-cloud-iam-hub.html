Flujo del proyecto
🟢 Onboarding — dar acceso en las 3 nubes de un golpe

El frontend dispara la intención

El sitio estático en Cloud Storage hace un fetch() con POST /onboard a la API en Cloud Run (FastAPI), incluyendo el header X-Api-Key. Sin esa key válida (guardada en Secret Manager), la API responde 401 antes de tocar el IdentityService.

Se guarda la intención, no la ejecución

El IdentityService escribe en Firestore un Identity y N Assignment (uno por nube). Esto es clave: el hub separa "qué se quiere" de "cómo se ejecuta" en cada proveedor.

Fan-out paralelo hacia los Adapters

El propio IdentityService dispara, con asyncio.gather, al GcpAdapter, AwsAdapter y AzureAdapter en paralelo — todos implementan la misma interfaz CloudAdapter. (En el diagrama original esto lo hacía Eventarc + Cloud Run Workers; es el primer paso del roadmap.)

Cada Adapter habla el idioma nativo de su nube

GcpAdapter: getIamPolicy → mutar bindings → setIamPolicy(etag), el patrón read-modify-write obligatorio en GCP. AwsAdapter: crea usuario y adjunta policies vía boto3. AzureAdapter: crea identidad en Entra ID (Graph) y asigna rol vía Azure RBAC.

Trazabilidad cross-cloud

Cada Adapter escribe un registro en la colección Audit (actor, acción, provider, before/after, correlationId) → una sola fuente de verdad para auditar acceso en 3 nubes distintas, consultable vía GET /audit.

🔴 Offboarding — revocar acceso en las 3 nubes de un golpe

Misma entrada, efecto inverso

POST /offboard reutiliza exactamente el mismo pipeline (Firestore → Eventarc → Workers → Adapters), pero cada Adapter ejecuta su lógica de revocación.

La revocación no es igual en cada nube

Azure: accountEnabled=false en Entra ID. GCP: se quita el binding con etag vigente. AWS: no existe "disable user" — se desactivan access keys, se elimina el login profile y se desasocian policies/grupos (o se adjunta un DenyAll).

Plan B en tarima

Flag CLOUD_IAM_MODE=sandbox conmuta los Adapters a modo mock (misma interfaz, sin llamadas reales). Si falla la red o las credenciales en vivo, la demo sigue funcionando.

Encuadre para la charla: esto es la abstracción que por dentro venden plataformas de CIEM (Wiz, Prisma Cloud) e IGA (SailPoint). La diferencia es que aquí construimos el orquestador, no lo compramos — y el cerebro vive en GCP, gobernando AWS y Azure desde ahí.
Nota de seguridad del propio demo: el frontend es un sitio público en Cloud Storage y la API de Cloud Run acepta invocaciones sin autenticación IAM — cualquiera con la URL podría llamarla. Por eso POST /onboard, POST /offboard y GET /audit exigen el header X-Api-Key, validado dentro de la propia app contra un secreto generado por Terraform en Secret Manager. Sin la key correcta, la API responde 401 antes de tocar ninguna nube.
Sí se puede — pero no como esperas

🔧 GCP

setIamPolicy() reemplaza toda la política del recurso, no la mezcla. El patrón correcto es getIamPolicy → mutar los bindings en memoria → setIamPolicy enviando el etag obtenido, y reintentar si la API responde 409 ABORTED (carrera con otro escritor). Read-modify-write, no un simple "set".

🔧 AWS

No existe una API "disable user". El offboarding real es una composición de pasos: desactivar access keys, eliminar el login profile y desasociar policies/grupos (o adjuntar AWSDenyAll). Con IAM Identity Center (SSO) sí hay un disable directo en el store de identidades.

🔧 AZURE

Identidad y permisos viven en dos planos separados con dos SDKs distintos: Entra ID (Microsoft Graph) para la identidad y accountEnabled, y Azure RBAC para los roleAssignments sobre subscription / resource group / recurso. Se necesitan dos llamadas, no un solo assign().
